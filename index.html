SOLID Principles in Java

1. Single Responsibility Principle (SRP)

Definition: A class should have only one reason to change - it should have only one job.

❌ BAD - Multiple Responsibilities

class User {
    private String name;
    private String email;
    
    void saveToDatabase() {
        // Database logic
    }
    
    void sendEmail() {
        // Email logic
    }
    
    void generateReport() {
        // Report logic
    }
}

✅ GOOD - Single Responsibility

class User {
    private String name;
    private String email;
    // Only user data
}

class UserRepository {
    void save(User user) {
        // Database operations
    }
}

class EmailService {
    void send(User user, String message) {
        // Email operations
    }
}

2. Open/Closed Principle (OCP)

Definition: Open for extension, closed for modification.

❌ BAD - Must modify for each new type

class PaymentProcessor {
    void process(String type, double amount) {
        if (type.equals("credit_card")) {
            // Process credit card
        } else if (type.equals("paypal")) {
            // Process PayPal
        }
        // Add new type? Modify this class!
    }
}

✅ GOOD - Extend without modifying

interface PaymentMethod {
    void pay(double amount);
}

class CreditCardPayment implements PaymentMethod {
    public void pay(double amount) {
        // Credit card logic
    }
}

class PayPalPayment implements PaymentMethod {
    public void pay(double amount) {
        // PayPal logic
    }

// Add new payment? Just create new class!

3. Liskov Substitution Principle (LSP)

Definition: Subtypes must be substitutable for their base types.

// ❌ VIOLATES LSP
interface Bird {
    void fly();
}

class Penguin implements Bird {
    public void fly() {
        throw new UnsupportedOperationException();
        // Penguin can't fly!
    }
}

// ✅ CORRECT DESIGN
interface Bird {
    void move();
}

interface FlyingBird extends Bird {
    void fly();
}

class Sparrow implements FlyingBird {
    public void fly() { }
    public void move() { }
}

class Penguin implements Bird {
    public void move() { /* swim */ }
}

4. Interface Segregation Principle (ISP)

Definition: Clients should not depend on interfaces they don't use.

❌ BAD - Fat Interface

interface Worker {
    void work();
    void eat();
    void sleep();
}

class Robot implements Worker {
    public void work() { }
    public void eat() { 
        throw new Error(); // Robot can't eat!
    }
    public void sleep() { 
        throw new Error(); // Robot can't sleep!
    }
}

✅ GOOD - Segregated Interfaces

interface Workable { void work(); }
interface Eatable { void eat(); }
interface Sleepable { void sleep(); }

class Human implements Workable, Eatable, Sleepable {
    public void work() { }
    public void eat() { }
    public void sleep() { }
}

class Robot implements Workable {
    public void work() { }
    // Only implements what it needs
}

5. Dependency Inversion Principle (DIP)

Definition: Depend on abstractions, not concrete implementations.

// ❌ BAD - High level depends on low level
class PaymentService {
    private CreditCardPayment creditCard = new CreditCardPayment();
    
    void pay(double amount) {
        creditCard.process(amount);
    }
}

// ✅ GOOD - Depend on abstraction
interface PaymentGateway {
    void process(double amount);
}

class PaymentService {
    private PaymentGateway gateway;
    
    PaymentService(PaymentGateway gateway) {
        this.gateway = gateway; // Injected!
    }
    
    void pay(double amount) {
        gateway.process(amount);
    }
}
✓ SOLID Benefits:
  • Code is maintainable and flexible
  • Easy to test with mocks
  • Reduced coupling
  • Easy to extend without breaking code

LRU Cache Implementation

Medium Difficulty

Problem Statement:

Implement an LRU (Least Recently Used) Cache with O(1) get and put operations.

  • get(key) - return value or -1 if not found
  • put(key, value) - set or update value
  • When capacity exceeded, evict least recently used
  • Both operations must be O(1)

Key Idea: HashMap + Doubly Linked List

Most Recent (Tail) <-- Node <-- Node <-- Node (Head) Least Recent HashMap: {key -> Node} Doubly LinkedList: Tracks usage order On get/put: Move node to tail (most recent) On evict: Remove head (least recent)

Complete Implementation

class LRUCache {
    private int capacity;
    private Map<Integer, Node> cache;
    private Node head;  // dummy head (least recent)
    private Node tail;  // dummy tail (most recent)

    private class Node {
        int key, value;
        Node prev, next;
        
        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    public LRUCache(int capacity) {
        this.capacity = capacity;
        this.cache = new HashMap<>();
        this.head = new Node(0, 0);
        this.tail = new Node(0, 0);
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        if (!cache.containsKey(key)) {
            return -1;
        }
        
        Node node = cache.get(key);
        moveToTail(node);  // Mark as recently used
        return node.value;
    }

    public void put(int key, int value) {
        if (cache.containsKey(key)) {
            // Update existing
            Node node = cache.get(key);
            node.value = value;
            moveToTail(node);
        } else {
            // Add new
            if (cache.size() == capacity) {
                removeNode(head.next);  // Remove LRU
            }
            Node newNode = new Node(key, value);
            cache.put(key, newNode);
            addToTail(newNode);
        }
    }

    private void moveToTail(Node node) {
        removeNode(node);
        addToTail(node);
    }

    private void removeNode(Node node) {
        cache.remove(node.key);
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void addToTail(Node node) {
        node.prev = tail.prev;
        node.next = tail;
        tail.prev.next = node;
        tail.prev = node;
    }
}

// Usage Example:
LRUCache cache = new LRUCache(2);
cache.put(1, 1);
cache.put(2, 2);
System.out.println(cache.get(1));  // 1
cache.put(3, 3);  // Evicts key 2
System.out.println(cache.get(2));  // -1 (evicted)

Complexity Analysis

Operation Time Complexity Why
get(key) O(1) HashMap lookup + list operations
put(key, value) O(1) HashMap insert + list operations
Overall Space O(capacity) Store at most capacity items
✓ Key Points to Remember:
  • HashMap gives O(1) lookups
  • Doubly LinkedList maintains order
  • Tail = most recently used
  • Head = least recently used
  • On access, move node to tail
  • On eviction, remove head.next

Rate Limiter Design

Medium Difficulty

Problem Statement:

Design a rate limiter that allows at most N requests per second from a user.

  • allowRequest() returns true/false
  • Must handle distributed systems
  • Support bursts (Token Bucket)

Algorithm 1: Token Bucket

Bucket has capacity tokens Refills at rate R tokens/second Request arrives: - Has token? → Process + Remove token → ALLOW - No token? → REJECT Allows bursts up to capacity!
class TokenBucketRateLimiter {
    private final int capacity;
    private final double refillRate;  // tokens per second
    private double tokens;
    private long lastRefillTime;

    public TokenBucketRateLimiter(int capacity, double refillRate) {
        this.capacity = capacity;
        this.refillRate = refillRate;
        this.tokens = capacity;
        this.lastRefillTime = System.currentTimeMillis();
    }

    public synchronized boolean allowRequest() {
        refillTokens();
        
        if (tokens >= 1.0) {
            tokens -= 1.0;
            return true;
        }
        return false;
    }

    private void refillTokens() {
        long now = System.currentTimeMillis();
        long timePassed = now - lastRefillTime;
        
        // Calculate tokens to add
        double tokensToAdd = (timePassed / 1000.0) * refillRate;
        tokens = Math.min(capacity, tokens + tokensToAdd);
        lastRefillTime = now;
    }
}

// Usage:
TokenBucketRateLimiter limiter = 
    new TokenBucketRateLimiter(10, 5);  // 10 capacity, 5/sec
    
for (int i = 0; i < 15; i++) {
    if (limiter.allowRequest()) {
        System.out.println("Request " + i + " allowed");
    } else {
        System.out.println("Request " + i + " rejected");
    }
}

Algorithm 2: Sliding Window

class SlidingWindowRateLimiter {
    private Queue<Long> requestTimes;
    private int maxRequests;
    private long windowSizeMs;

    public SlidingWindowRateLimiter(int maxRequests, long windowSizeMs) {
        this.requestTimes = new LinkedList<>();
        this.maxRequests = maxRequests;
        this.windowSizeMs = windowSizeMs;
    }

    public synchronized boolean allowRequest() {
        long now = System.currentTimeMillis();
        long windowStart = now - windowSizeMs;
        
        // Remove requests outside current window
        while (!requestTimes.isEmpty() && 
               requestTimes.peek() < windowStart) {
            requestTimes.poll();
        }
        
        if (requestTimes.size() < maxRequests) {
            requestTimes.offer(now);
            return true;
        }
        return false;
    }
}

// Usage: 5 requests per 1000ms (1 second)
SlidingWindowRateLimiter limiter = 
    new SlidingWindowRateLimiter(5, 1000);

Comparison

Algorithm Pros Cons Use Case
Token Bucket Handles bursts, smooth Complex API rate limiting
Sliding Window Simple, accurate High memory Login attempts
Leaky Bucket Smooth output Less flexible Queue processing
✓ When to Use Which:
  • Token Bucket: APIs allowing bursts (payment processing)
  • Sliding Window: Strict limits (5 logins/minute)
  • Leaky Bucket: Constant output rate needed

Parking Lot System Design

Hard Difficulty

Problem Statement:

Design a multi-level parking lot with different spot types.

  • Support compact, small, large vehicles
  • Track parked vehicles
  • Find nearest available spot

Architecture

ParkingLot ├── Level 0 │ ├── ParkingSpot 0 (LARGE) │ ├── ParkingSpot 1 (LARGE) │ ├── ParkingSpot 2 (SMALL) │ └── ParkingSpot 3 (COMPACT) ├── Level 1 │ └── ... └── Level 2 └── ...

Implementation Code

enum VehicleSize { COMPACT, SMALL, LARGE }

class Vehicle {
    String licensePlate;
    VehicleSize size;
    
    Vehicle(String plate, VehicleSize size) {
        this.licensePlate = plate;
        this.size = size;
    }
}

class ParkingSpot {
    int spotId;
    VehicleSize spotSize;
    Vehicle vehicle;
    
    ParkingSpot(int spotId, VehicleSize spotSize) {
        this.spotId = spotId;
        this.spotSize = spotSize;
    }
    
    boolean isAvailable() {
        return vehicle == null;
    }
    
    boolean canFitVehicle(Vehicle v) {
        if (!isAvailable()) return false;
        if (spotSize == VehicleSize.COMPACT) {
            return v.size == VehicleSize.COMPACT;
        } else if (spotSize == VehicleSize.SMALL) {
            return v.size != VehicleSize.LARGE;
        }
        return true;
    }
    
    void parkVehicle(Vehicle v) {
        if (canFitVehicle(v)) {
            this.vehicle = v;
        }
    }
    
    void unparkVehicle() {
        this.vehicle = null;
    }
}

class Level {
    int levelNumber;
    List<ParkingSpot> spots;
    
    Level(int levelNumber, int numSpots) {
        this.levelNumber = levelNumber;
        this.spots = new ArrayList<>();
        
        for (int i = 0; i < numSpots; i++) {
            VehicleSize size;
            if (i < numSpots / 2) {
                size = VehicleSize.LARGE;
            } else if (i < 3 * numSpots / 4) {
                size = VehicleSize.SMALL;
            } else {
                size = VehicleSize.COMPACT;
            }
            spots.add(new ParkingSpot(i, size));
        }
    }
    
    ParkingSpot findAvailableSpot(Vehicle vehicle) {
        for (ParkingSpot spot : spots) {
            if (spot.canFitVehicle(vehicle)) {
                return spot;
            }
        }
        return null;
    }
    
    boolean parkVehicle(Vehicle vehicle) {
        ParkingSpot spot = findAvailableSpot(vehicle);
        if (spot != null) {
            spot.parkVehicle(vehicle);
            return true;
        }
        return false;
    }
    
    boolean unparkVehicle(String licensePlate) {
        for (ParkingSpot spot : spots) {
            if (spot.vehicle != null && 
                spot.vehicle.licensePlate.equals(licensePlate)) {
                spot.unparkVehicle();
                return true;
            }
        }
        return false;
    }
}

class ParkingLot {
    List<Level> levels;
    Map<String, Integer> vehicleLocationMap;
    
    ParkingLot(int numLevels, int spotsPerLevel) {
        this.levels = new ArrayList<>();
        this.vehicleLocationMap = new HashMap<>();
        
        for (int i = 0; i < numLevels; i++) {
            levels.add(new Level(i, spotsPerLevel));
        }
    }
    
    boolean parkVehicle(Vehicle vehicle) {
        for (Level level : levels) {
            if (level.parkVehicle(vehicle)) {
                vehicleLocationMap.put(vehicle.licensePlate, 
                                      level.levelNumber);
                System.out.println("Parked at Level " + 
                    level.levelNumber);
                return true;
            }
        }
        System.out.println("No available spot");
        return false;
    }
    
    boolean unparkVehicle(String licensePlate) {
        Integer levelNum = vehicleLocationMap.get(licensePlate);
        if (levelNum != null) {
            if (levels.get(levelNum).unparkVehicle(licensePlate)) {
                vehicleLocationMap.remove(licensePlate);
                return true;
            }
        }
        return false;
    }
}

// Usage Example:
ParkingLot lot = new ParkingLot(3, 20);
Vehicle compact = new Vehicle("ABC123", VehicleSize.COMPACT);
Vehicle large = new Vehicle("XYZ789", VehicleSize.LARGE);

lot.parkVehicle(compact);
lot.parkVehicle(large);
lot.unparkVehicle("ABC123");
✓ Design Patterns Used:
  • Strategy Pattern: Different vehicle sizes
  • Composite Pattern: Level hierarchy
  • Observer Pattern: Spot tracking

Design Patterns for Interviews

1. Singleton Pattern

Use Case: Database connections, Logger

class DatabaseConnection {
    private static volatile DatabaseConnection instance;
    
    private DatabaseConnection() {}
    
    public static DatabaseConnection getInstance() {
        if (instance == null) {
            synchronized (DatabaseConnection.class) {
                if (instance == null) {
                    instance = new DatabaseConnection();
                }
            }
        }
        return instance;
    }
}

2. Factory Pattern

Use Case: Creating objects without knowing concrete class

interface DataStore {
    void save(String data);
}

class DatabaseStore implements DataStore {
    public void save(String data) { }
}

class FileStore implements DataStore {
    public void save(String data) { }
}

class DataStoreFactory {
    public static DataStore create(String type) {
        switch(type) {
            case "db": return new DatabaseStore();
            case "file": return new FileStore();
            default: throw new IllegalArgumentException();
        }
    }
}

DataStore store = DataStoreFactory.create("db");
store.save("myData");

3. Builder Pattern

Use Case: Complex object construction

class User {
    private String name, email, phone;
    private int age;
    
    private User(UserBuilder builder) {
        this.name = builder.name;
        this.email = builder.email;
        this.age = builder.age;
        this.phone = builder.phone;
    }
    
    public static class UserBuilder {
        private String name, email, phone;
        private int age;
        
        public UserBuilder(String name, String email) {
            this.name = name;
            this.email = email;
        }
        
        public UserBuilder age(int age) {
            this.age = age;
            return this;
        }
        
        public UserBuilder phone(String phone) {
            this.phone = phone;
            return this;
        }
        
        public User build() {
            return new User(this);
        }
    }
}

User user = new User.UserBuilder("John", "john@email.com")
    .age(30)
    .phone("555-1234")
    .build();

4. Observer Pattern

Use Case: Event notifications

interface Observer {
    void update(String event);
}

class EventSource {
    private List<Observer> observers = new ArrayList<>();
    
    public void subscribe(Observer observer) {
        observers.add(observer);
    }
    
    public void notifyObservers(String event) {
        for (Observer obs : observers) {
            obs.update(event);
        }
    }
}

class EmailNotifier implements Observer {
    public void update(String event) {
        System.out.println("Email: " + event);
    }
}

EventSource source = new EventSource();
source.subscribe(new EmailNotifier());
source.notifyObservers("User registered");

5. Strategy Pattern

Use Case: Different algorithms for same operation

interface PaymentStrategy {
    void pay(double amount);
}

class CreditCardPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Paying $" + amount + " via CC");
    }
}

class ShoppingCart {
    private PaymentStrategy strategy;
    
    public void setPaymentMethod(PaymentStrategy s) {
        this.strategy = s;
    }
    
    public void checkout(double amount) {
        strategy.pay(amount);
    }
}

ShoppingCart cart = new ShoppingCart();
cart.setPaymentMethod(new CreditCardPayment());
cart.checkout(99.99);

System Design Interview Tips

Before Interview (2-4 Weeks)

  • Master LRU Cache: Most common LLD problem
  • Learn SOLID: Asked in almost every interview
  • 3-4 Design Patterns: Singleton, Factory, Builder, Observer
  • 2-3 HLD Problems: Twitter Feed, URL Shortener, Cache
  • Database Basics: SQL vs NoSQL, indexing, sharding
  • Caching Strategy: Redis, TTL, invalidation

During Interview

✓ DO:
  • Ask clarifying questions first
  • State your assumptions clearly
  • Draw diagrams while explaining
  • Discuss trade-offs
  • Start simple, then optimize
  • Write clean, readable code
  • Explain design decisions
  • Talk through your logic
✗ DON'T:
  • Jump to coding immediately
  • Over-complicate simple problems
  • Ignore edge cases
  • Write code without explanation
  • Claim perfection
  • Forget about thread-safety
  • Ignore scalability concerns

For 2-Year Experience Level

Focus On:
  • LLD with clear OOP design
  • Data structure implementations
  • Design patterns and SOLID
  • Basic system components
  • Thread safety basics

Interview Flow Example

Interview: "Design a URL shortener"

1. ASK QUESTIONS (5 min)
   - How many URLs per day?
   - Read/write ratio?
   - How long to keep URLs?
   - Global or single region?

2. PROPOSE ARCHITECTURE (5 min)
   - Database schema
   - API design
   - Caching strategy
   - Encoding method

3. DETAILED DESIGN (10 min)
   - Write key classes
   - Explain algorithms
   - Handle edge cases

4. DISCUSS TRADE-OFFS (5 min)
   - Consistency vs availability
   - Hashing vs sequential ID
   - Caching strategy

5. OPTIMIZATION (5 min)
   - How to scale?
   - Failure handling?
   - Monitoring/metrics?
